## Описание

В дампе зафиксирована обычная жизнь маленькой сети метеопоста: контроллер пингует шлюз, ходит
на локальный DNS и на погодный веб-сервер. Среди привычных адресов есть один лишний — внешний
адрес, на который уходит ровно 25 ICMP-запросов. Это классический ICMP-туннель: данные выносят
наружу полезной нагрузкой ping-пакетов. Задача — заметить аномалию, собрать блоки в правильном
порядке и вытащить из архива флаг.

## Решение

1. Открыть `tomsk_traffic.pcap` в Wireshark и перейти в **Statistics → Conversations → IPv4**.
   В списке четыре ключевых узла: шлюз `192.168.70.1` (300 пакетов штатного ping), локальный DNS
   `192.168.70.2`, погодный веб-сервер `82.200.115.4` и внешний `195.208.10.42` — ровно **25**
   ICMP-запросов.
2. Поставить фильтр `ip.dst == 195.208.10.42 and icmp.type == 8`. В **Packet bytes** полезная
   нагрузка начинается с `50 4b 03 04` — сигнатура ZIP; в текстовой колонке видно `PK......to`.
3. Полезная нагрузка — 32 байта (последний блок 10 байт), всего 778 байт. Блоки пронумерованы
   полем `icmp.seq` от 1 до 25. Порядок прихода нарушен: seq=5 пришёл раньше seq=4, ещё две
   инверсии — 12/11 и 19/18. Перед сборкой блоки нужно отсортировать по `icmp.seq`.
4. Склеить поле `data` в порядке seq и сохранить как `leaked.zip`. В архиве два файла:
   `tom_river_telemetry.txt` и `sensor_notes.log`. В сводке телеметрии лежит ключ подтверждения —
   это и есть флаг.

Сборка одной строкой:

```sh
tshark -r tomsk_traffic.pcap -Y "ip.dst == 195.208.10.42 and icmp.type == 8" \
  -T fields -e icmp.seq -e data | sort -n -k1,1 | awk '{print $2}' \
  | tr -d '\r\n' | xxd -r -p > leaked.zip
unzip -o leaked.zip && grep -r tomskfsp .
```

[Эксплоит](solve/solve.py) — без зависимостей, сам разбирает pcap и собирает архив:

```sh
python solve/solve.py public/tomsk_traffic.pcap -o leaked.zip --flag
```
